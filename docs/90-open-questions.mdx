## Q1：Python 工具鏈與目錄佈局

**題目**：用 uv 還是 pip／venv？Python 版本？實驗程式放哪個目錄、怎麼分層？

**為什麼現在要決定**：`CLAUDE.md` 原本寫「等寫第一行實驗程式碼時再定，不預先猜」。那個時間點就是現在——10/26–11/01 這格要產出 split、reveal manifest 與 TF-IDF 特徵。

**影響範圍**：研究規格 11.2、所有實驗程式、可重現性宣稱。

**可選方案**：

| 方案 | 優點 | 代價 |
| --- | --- | --- |
| uv + `src/splitsense/` 套件佈局 | 鎖定版本快、重現性好、與 `pyproject.toml` 一致 | 需要先學工具 |
| pip + venv + `requirements.txt` | 最熟悉、課堂示範常見 | 版本鎖定較弱 |
| 只用 notebook，不建套件 | 最快出圖、簡報素材直接來自 notebook | 洩漏檢查測試難寫，重跑一致性難保證 |

**決議（2026-10-31）：uv + `src/splitsense/` 套件佈局 + `pyproject.toml`。** Python 要求 `>=3.12`，本機釘 3.13。相依為 numpy、pandas、pyarrow、scikit-learn、matplotlib，開發用 pytest 與 ruff，版本鎖在 `uv.lock`。

**理由**：研究規格 8.4 的重現性宣稱（固定 seed 重跑得到相同 split 與評估結果）需要鎖版本；洩漏檢查那七條要寫成 pytest，notebook 擺不下。

**實際佈局**：

```text
src/splitsense/   config.py  data.py  eda.py  split.py  reveal.py
scripts/          run_eda.py  build_dataset.py
tests/            conftest.py  test_leakage.py  test_reproducibility.py
data/             原始 parquet（.gitignore）
artifacts/        eda/  manifests/（.gitignore）
```

**狀態**：:badge[已決議]{variant="success"}

## Q2：繁中 pilot 是否與課堂版並行啟動

**題目**：繁中 pilot 照 10/19 定案擱到 12/21 之後，還是現在就開始招募標註者？

**為什麼是個問題**：招募 3 至 5 位組外標註者、寫標註規範、做 20–30 筆校準，前置期很長。若論文確定要做，現在開始的成本遠低於期末後才開始；但那會吃掉課堂版的時間，而課堂版目前已落後約一週。

**影響範圍**：研究規格 4.1、6.5、10.2。

**決議（2026-10-31）：不並行啟動。** 繁中 pilot 照 10/19 定案留在論文延伸，課堂版期間不招募標註者、不寫標註規範、不做校準。

**理由**：課堂版此時已落後約一週半，`10/26–11/01` 這格（split、reveal manifest、TF-IDF、兩個基準）尚未開始。pilot 的前置工作無法壓縮，並行只會讓兩邊都延誤；而課堂版的最低成功線（研究規格 10.3）不含繁中證據，先把它做完才是正確的優先順序。

**代價**（接論文時要補的時間）：招募 3 至 5 位組外標註者、撰寫標註規範、20–30 筆校準，整段從 12/21 之後才開始。論文的 H4（繁中結果需獨立成立）在那之前都沒有證據。

## Q4：TF-IDF 的具體設定

**題目**：`ngram_range`、`min_df`、`max_features`、是否 sublinear scaling、是否移除 stopwords？

**為什麼不能隨便填**：文字中位數只有 60 字元（見 Dataset Card 第 3 節），很短。`max_features` 開太大在這種短文本上多半只是增加噪音與調參時間。

**影響範圍**：研究規格 7.2、整個課堂版主線的特徵。

**注意**：這些設定屬於特徵決策，**只能由 training 決定**（研究規格 6.4 第 6 條）。

## Q5：163 筆重複文字要去重還是合併

**題目**：31,766 個 item 對應 31,603 段不同文字。重複的要整段丟掉、保留其中一筆，還是把多個 item 的標註合併成一筆？

**影響範圍**：研究規格 6.2、split manifest、item 總數與所有統計。

**約束**：無論選哪個，都必須在切 split 前完成，避免同一段文字同時落在 train 與 test。合併會讓該 item 的標註數不等於 3，與「只取恰好 3 份」的前提衝突，需額外處理。

**決議（2026-10-31）：去重，每段文字只保留第一個 item（以 `item_id` 排序後取第一筆）。** 實作於 `data.build_items(dedup_text=True)`，去重後 **31,603** 個 item、94,809 筆 annotation。

**理由**：合併會打破固定分母的前提，而固定分母正是切斷「標註數洩漏答案」那條路徑的手段（研究規格 6.4 第 7 條）。為 163 筆（0.5%）破壞一個核心不變量不值得。

**副作用**：Dataset Card 3.1–3.3 的統計是去重前算的，與管線實際使用的數字有 0.1 至 0.6 個百分點的差異。已在 Dataset Card 3.4 併列兩組數字，並註明引用時以去重後為準。

**狀態**：:badge[已決議]{variant="success"}

## Q6：OpenSpec 是否在課堂版期間續用

**題目**：repo 已導入 OpenSpec（commit `abb2898`），`openspec/config.yaml` 宣告 `openspec/specs/` 擁有實驗程式的行為。課堂版期間要實際使用，還是暫停？

**影響範圍**：開發流程、`openspec/config.yaml`、`CLAUDE.md` 的文件分工敘述、研究規格 1.2。

**討論結論（2026-10-29，待確認）**：課堂版期間暫停使用，12/21 之後若接論文延伸再評估。理由是單人、六週、程式不列入交件的情況下，「筆記 → 研究規格 → SHALL/Scenario → 程式」四層的比例不對，而目前的首要風險正是時間花在文件而非程式。唯一值得規格化的洩漏檢查（研究規格 6.4）已是七條編號清單，可直接對應測試案例，不需要中間層。

**決議（2026-10-31）：課堂版期間暫停使用**，12/21 之後若接論文延伸再評估。`openspec/` 目錄保留（那份 config 的 hard rules 之後接論文時有價值），但 `openspec/config.yaml` 與 `CLAUDE.md` 已註明暫停。

**取而代之的驅動方式**：課堂版時程（研究規格 10.1）當計畫；`tests/test_leakage.py` 與 `tests/test_reproducibility.py` 當不變量規格；本文件當決策紀錄。

**狀態**：:badge[已決議]{variant="success"}
