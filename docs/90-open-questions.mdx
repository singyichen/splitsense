## Q1：Python 工具鏈與目錄佈局

**題目**：用 uv 還是 pip／venv？Python 版本？實驗程式放哪個目錄、怎麼分層？

**為什麼現在要決定**：`CLAUDE.md` 原本寫「等寫第一行實驗程式碼時再定，不預先猜」。那個時間點就是現在——10/26–11/01 這格要產出 split、reveal manifest 與 TF-IDF 特徵。

**影響範圍**：研究規格 11.2、所有實驗程式、可重現性宣稱。

**可選方案**：

| 方案 | 優點 | 代價 |
| --- | --- | --- |
| uv + `src/splitsense/` 套件佈局 | 鎖定版本快、重現性好、與 `pyproject.toml` 一致 | 需要先學工具 |
| pip + venv + `requirements.txt` | 最熟悉、課堂示範常見 | 版本鎖定較弱 |
| 只用 notebook，不建套件 | 最快出圖、簡報素材直接來自 notebook | 洩漏檢查測試難寫，重跑一致性難保證 |

**決議（2026-10-31）：uv + `src/splitsense/` 套件佈局 + `pyproject.toml`。** Python 要求 `>=3.12`，本機釘 3.13。相依為 numpy、pandas、pyarrow、scikit-learn、matplotlib，開發用 pytest 與 ruff，版本鎖在 `uv.lock`。

**理由**：研究規格 8.4 的重現性宣稱（固定 seed 重跑得到相同 split 與評估結果）需要鎖版本；洩漏檢查那七條要寫成 pytest，notebook 擺不下。

**實際佈局**：

```text
src/splitsense/   config.py  data.py  eda.py  split.py  reveal.py
scripts/          run_eda.py  build_dataset.py
tests/            conftest.py  test_leakage.py  test_reproducibility.py
data/             原始 parquet（.gitignore）
artifacts/        eda/  manifests/（.gitignore）
```

## Q3：階梯 3 選 Random Forest 還是 Gradient Boosting

**題目**：研究規格 7.1 寫「Random Forest 或 Gradient Boosting」，要選哪一個？

**影響範圍**：調參格線（RF 調 `n_estimators`、`max_depth`；GB 調 `n_estimators`、`learning_rate`、`max_depth`）、`GridSearchCV` 的執行時間。

**提醒**：進度落後時的刪減順序第 2 條是「樹模型只留一個」，所以即使兩個都做，也要先決定哪一個是會留下來的那個。

**決議（2026-10-31）：Gradient Boosting**，實作為 `HistGradientBoostingClassifier` + `TruncatedSVD(n_components=200)`，調 `learning_rate` 與 `max_depth`。

**理由**：TF-IDF 是 31,451 維稀疏矩陣，Random Forest 的 `max_depth` 格線在這種高維稀疏輸入上很難調得好，而 `HistGradientBoostingClassifier` 搭配降維後速度與表現都更可控。

**實測後的附帶結論**：非線性模型在這個任務上**沒有實質增益**。PR-AUC 44.6 對 Logistic Regression 的 42.8（+1.8 個百分點），但主要指標 `R@10%` 完全相同（都是 19.4，標準差重疊），調參耗時 111 秒對 10 秒。依研究規格 8.7 的決策規則，結論採 Logistic Regression——透明、快、係數可讀。樹模型留在報告裡當「檢查過非線性」的證據。

**狀態**：:badge[已決議]{variant="success"}

## Q4：TF-IDF 的具體設定

**題目**：`ngram_range`、`min_df`、`max_features`、是否 sublinear scaling、是否移除 stopwords？

**為什麼不能隨便填**：文字中位數只有 60 字元（見 Dataset Card 第 3 節），很短。`max_features` 開太大在這種短文本上多半只是增加噪音與調參時間。

**影響範圍**：研究規格 7.2、整個課堂版主線的特徵。

**注意**：這些設定屬於特徵決策，**只能由 training 決定**（研究規格 6.4 第 6 條）。

**決議（2026-10-31）**：

| 參數 | 值 |
| --- | --- |
| `ngram_range` | `(1, 2)` |
| `min_df` | `2` |
| `max_features` | `50000` |
| `sublinear_tf` | `True` |
| `stop_words` | `None`（不移除） |
| `strip_accents` | `"unicode"` |

實作於 `features.TFIDF_PARAMS`，只在 training 文字上 `fit`（有測試守著：test 專屬的詞不得進詞彙表）。

**不移除 stopwords 的理由**：文字中位數只有 60 字元，否定詞、程度詞與模糊詞本身就是分歧訊號（研究規格 8.6 的錯誤類型），移除等於丟掉要預測的東西。

**狀態**：:badge[已決議]{variant="success"}

## Q5：163 筆重複文字要去重還是合併

**題目**：31,766 個 item 對應 31,603 段不同文字。重複的要整段丟掉、保留其中一筆，還是把多個 item 的標註合併成一筆？

**影響範圍**：研究規格 6.2、split manifest、item 總數與所有統計。

**約束**：無論選哪個，都必須在切 split 前完成，避免同一段文字同時落在 train 與 test。合併會讓該 item 的標註數不等於 3，與「只取恰好 3 份」的前提衝突，需額外處理。

**決議（2026-10-31）：去重，每段文字只保留第一個 item（以 `item_id` 排序後取第一筆）。** 實作於 `data.build_items(dedup_text=True)`，去重後 **31,603** 個 item、94,809 筆 annotation。

**理由**：合併會打破固定分母的前提，而固定分母正是切斷「標註數洩漏答案」那條路徑的手段（研究規格 6.4 第 7 條）。為 163 筆（0.5%）破壞一個核心不變量不值得。

**副作用**：Dataset Card 3.1–3.3 的統計是去重前算的，與管線實際使用的數字有 0.1 至 0.6 個百分點的差異。已在 Dataset Card 3.4 併列兩組數字，並註明引用時以去重後為準。

**狀態**：:badge[已決議]{variant="success"}

## Q11：主要指標的評估範圍——full 還是 hard

**題目**：`Recall@10%` 要在整個 test split（full）上算，還是在「可見 2 份一致」的子集（hard）上算，還是兩者並列而以其中一個為主？

**為什麼現在才發現**：這是跑完階梯 0 與 1 之後才量出來的（2026-10-31）。研究規格 8.2 原本把主要指標定在整個測試集上，但實測顯示那個設定下指標已飽和。

**證據**：

| 事實 | 數字 |
| --- | ---: |
| test item 數 | 4,741 |
| 可見 2 份不一致的 item（必然分歧） | 1,588（33.5%） |
| 這批的 `z=1` 比例 | 100% |
| 預算 10% 的名額 `K` | 474 |

確定陽性 1,588 遠超過名額 474，所以任何把它們排前面的方法都拿到 `P@10%` = 100%、`R@10%` = 理論上限 20.1%。可見標籤 entropy 規則實測正是 `100.0 ± 0.0` 與 `20.1 ± 0.0`。**在 full 範圍下，沒有任何模型能勝過那條規則**——不是因為規則很強，而是因為指標撞到天花板。要讓 full 範圍有區分力，預算必須大於 33.5%。

在 hard 範圍下，可見 entropy 恆為 0、完全沒有排序資訊，實測與隨機無法區分（PR-AUC 24.7 對 24.9，兩者都約等於盛行率 24.67%）。這個子集的地板線是隨機約 10%，H2 在這裡才可檢驗。

**可選方案**：

| 方案 | 優點 | 代價 |
| --- | --- | --- |
| 兩者並列，**以 hard 為主要** | 直接對應研究規格 2.2 的問題；H2 可檢驗；full 的飽和本身是個結論 | 主要指標在專案中途改過，簡報要交代清楚 |
| 只報 full | 不動原訂指標 | H2 無法檢驗，「ML 勝不過規則」的結論會是指標假象，不是真實發現 |
| 只報 full 但把預算提高到 40% | 不必改範圍 | 「只能複核 40% 資料」不符合研究規格 8.2 設定主要指標時的實務問句 |

**2026-10-31 補充的證據**：階梯 2 與 3 跑完後，hard 範圍的結果證實這個範圍可以區分模型——

| 模型 | PR-AUC | `R@10%` | `Lift@10%` |
| --- | ---: | ---: | ---: |
| Random | 24.9 ± 0.8 | 10.1 ± 0.9 | 1.02 |
| Visible entropy | 24.7 ± 0.3 | 10.6 ± 0.6 | 1.06 |
| Logistic Regression | 42.8 ± 1.4 | 19.4 ± 0.8 | 1.95 |
| Gradient Boosting | 44.6 ± 1.3 | 19.4 ± 0.6 | 1.94 |

模型把 `R@10%` 從規則的 10.6% 提到 19.4%，接近兩倍，而這個差距在 full 範圍下**完全看不到**（那裡所有方法都是 20.1%）。所以這不只是指標選擇的偏好問題：只報 full 範圍會讓整個專案的核心發現消失。

**建議**：第一個方案。full 的飽和不是壞消息——它正好對應研究規格 8.7 決策規則的第一列（「可見 entropy 已經最好 → 先採透明規則排序，不導入模型」），可以寫成「低預算時規則就夠了，真正需要模型的是前兩人暫時一致的那批」。這個敘事比原本的「比較四個模型的分數」更有說服力。

**影響範圍**：研究規格 8.2、8.2.1、8.4、簡報第 5 與第 6 段、H2 的檢驗方式。

**決議（2026-10-31）：兩個範圍並列報告，以 hard 為主要評估範圍。**

**理由**：模型與查表的 8.8 個百分點差距在 full 範圍完全看不到（那裡所有方法都是 20.1%），只報 full 會讓本專案的三個主要發現全部消失，而且會得出「ML 勝不過規則」這個**指標假象**而非真實結果。同時保留 full 範圍的報告，因為它的飽和本身就是結論——對應研究規格 8.7 決策規則第一列。

## Q12：full 範圍的模型分數怎麼排

**題目**：Q11 決議兩個範圍並列報告，但模型是**只在 hard 範圍上訓練**的。要在 full 範圍報它的分數時，該直接用模型對全部 test item 的輸出排序，還是先把「可見已不一致」那批排到最前面、模型只負責排剩下的？

**為什麼現在才發現**：研究規格 8.4 的 full 表原本只有 `Random` 與 `Visible entropy` 兩列，模型那兩列是空的——不填就碰不到這個問題。2026-11-09 要把 BGE-M3 加進兩個範圍時才必須決定。

**事實**：模型訓練時只看可見 2 份一致的 row，所以 `visible_disagree` 與 `visible_entropy` 這兩欄在訓練資料上全為零，L2 會把它們的係數壓成 0（研究規格 8.4.2 實測兩個模型都是 0.000）。換句話說，**模型沒有任何機會學到「可見不一致代表必然分歧」**。

**可選方案**：

| 方案 | 數字會長怎樣 | 問題 |
| --- | --- | --- |
| **部署式排序**：可見不一致者排最前，其餘依模型分數 | 所有方法 `R@10%` = 20.1 ± 0.0，PR-AUC 才有差（83.4 → 93.6） | 要在表下說明排序規則，否則讀者會以為是模型自己排出 100% 的 `P@10%` |
| 原始模型分數直接排 full | 模型會輸給 entropy 規則 | **誤導**。那不是模型能力的量測，是「拿只處理難題的模型去處理全部題目」的量測；而且實務上沒人會這樣部署 |
| full 範圍乾脆不報模型 | 不必決定 | 8.4 的 full 表會永遠留著兩個空格，而 Q11 說兩個範圍要並列 |

**決議（2026-11-09）：採部署式排序。**

**理由**：三個方案裡只有這一個同時符合實務部署方式與 Q11 的敘事。可見已不一致者必然分歧是**定義**，任何上線的排序都會先把它們送去複核；模型的工作是排剩下那批。而且這個排序方式讓 full 表真正發揮它的作用——證明指標在那裡已經壞掉：六個方法的 `P@10%` 全是 100.0 ± 0.0、`R@10%` 全是 20.1 ± 0.0，連 `bge-m3` 也一樣。這比留兩個空格有力得多。

**實作**：`baselines.disagree_first_scores(manifest, refine)`，分數為 `1(可見不一致) + 0.5 × clip(refine, 0, 1)`，確保 refine 不可能翻過 disagree 那一群。`Random` 與 `Visible entropy` 仍用原始分數（entropy 本身就是這條規則，不需要再組合）。

**影響範圍**：研究規格 8.2.1、8.4 的 full 表、`scripts/run_models.py`。hard 範圍完全不受影響，8.4 的 hard 表與 2026-10-31 的數字逐格相同。

**狀態**：:badge[已決議]{variant="success"}
